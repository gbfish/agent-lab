## 2026-09-05 · 三组对照:环 2 是 qwen3:14b 独有的怪癖,8b 反而 100% 格式正确;剩下的失败全是推理质量。别买 Mac

**改了什么变量:** 三组各改一个 —— A 开 toolshim;B 换 qwen2.5-coder:14b;C 换 qwen3:8b。其余同基线。

**配置:** goose 1.49.0 / `--no-profile --with-builtin developer --max-turns 20 --max-tool-repetitions 3` / 12 题 × 3 / M3 Pro 18GB
- A:`qwen3:14b-16k` + `GOOSE_TOOLSHIM=true GOOSE_TOOLSHIM_OLLAMA_MODEL=mistral-nemo`,timeout 1500
- B:`qwen2.5-coder:14b-16k`
- C:`qwen3:8b-32k`

**数据(全部用同一版 analyze.py 重算,t11 关键字修过后 regrade):**

| | 工具调用格式 | 任务完成 | 平均耗时 | 平均调用 | 主要失败 |
|---|---|---|---|---|---|
| 基线 qwen3:14b | 83.3% (30/36) | 80.6% (29/36) | 107s | 1.9 | 环 2 ×6(JSON 引号没转义被 Ollama 吞) |
| A toolshim + 14b | 97.2% (35/36) | **94.4% (34/36)** | **324s** | 5.1 | 解释器 27 次运行里解析失败 83 次,靠重试扛过去;1 次撞 max-turns |
| B qwen2.5-coder:14b | **0%** (0/36) | 0% | 5s | 0.0 | 把调用当纯文本 JSON 吐(有时带 ``` 围栏),Ollama 不解析,一轮就结束 |

分题稳定性(过/3):
- 基线 14b:t07 2、t08 2、t10 2、t11 2、t12 0,其余满
- toolshim:t11 2、t12 2,其余满
- 8b:t05 2、t09 2、t12 0,其余满

**手工读 trajectory 看到的:**
- **8b 一次调用都没被吞。** 说明「JSON 字符串里引号不转义」是 qwen3:14b 这个权重的怪癖,不是「模型小所以不会调工具」。反过来推:更大的模型未必更好,这条线上硬件没有确定收益。
- **toolshim 的代价:** 主模型和 mistral-nemo(7GB)加起来超过 GPU 预算,Ollama 每轮换入换出,耗时 ×3。解释器本身也不稳:模型给的是最终答案时它常常还硬凑一个 `unparseable_tool_call`,Goose 就再转一圈。t02 三次都这样,最多转了 13 次才把「端口 8731」说出来。
- **8b 的失败是「想错了」,不是「说不出来」:**
  - t05_r1:cwd 已经是 work/,它还写到 `work/out/README.md`。路径推理错(环 3)。
  - t09_r3:`tr` 转换其实成功了,工具返回 `(no output)`,它当失败连试三种写法,最后**把原文件 notes.txt 覆盖成了自己编的内容**。环 5,而且是破坏性的。同一模式在基线 t08_r2、8b t06_r2 也出现,只是那两次没造成损失。
  - t12 三次:都读了文件,都看到没错,都还是改了(改成 f-string,并在回答里承认「原代码本身没有语法错误」)。盲从前提(环 3)。14b 在 toolshim 下 2/3 能顶住,8b 0/3。
- **t11 关键字又漏了一次**(「未在…找到」)。answer_contains 这种判法脆,已加宽,但长期该换成让模型输出固定字段。

**结论 / 下一步:**
- **硬件:别买。** 四组数据没有一组指向「模型能力不够」:8b 格式满分;14b 的格式问题是特定怪癖且 toolshim 能救;剩下的失败(误读 (no output)、盲从、路径)是提示词和工具输出设计的问题,70B 大概率一样会犯,至少没有证据说它不会。9/22 的预订窗口可以放掉。
- **当前最佳配置:`qwen3:8b-32k` 裸跑。** 86% 完成、79s 一次、格式零失误。比 toolshim+14b 少 8 个百分点但快 4 倍,而且失败模式干净,全是能用提示词打的。
- **下一个变量(只改这一个):`--system` 加三条 —— `(no output)` 表示命令成功,用 cat 确认而不是重跑;改文件前先读,没坏别改;路径按 `<working-directory>` 用相对路径。** 8b 和 14b 各跑一遍,看 t05/t09/t12 能不能收回来。
- toolshim 想留着用的话,解释器换成 `qwen3:4b` 之类塞得下的,先测换入换出是否消失。
- 任务集要加:「(no output) 之后确认」、「没坏别改」、相对/绝对路径,这三类是现在真正的失败点。


## 2026-09-04 · 基线:qwen3:14b 工具调用 83%,主瓶颈是环 2(JSON 引号没转义,被 Ollama 静默丢弃)

**改了什么变量:** 无,这是基线。

**配置:** `qwen3:14b-16k` / goose 1.49.0 / `--no-profile --with-builtin developer --max-turns 20 --max-tool-repetitions 3` / 12 题 × 3 / M3 Pro 18GB

**数据(36 次,平均 107s/次,平均 1.9 次工具调用):**
- 工具调用格式正确率:**83.3%**(30/36)→ 落在 70–90% 「边缘」档
- 任务完成率:**80.6%**(29/36)
- 失败分布:环1 0 · **环2 6** · 环3 0 · 环4 0 · 环5 0 · 环6 1 · 环7 0 · 待人工 2
- 单步题(t01–t05)15/15 全过,多步题(t06–t10)13/15,无解题 t11 2/3,前提错误题 t12 0/3

**手工读 trajectory 看到的:**
- **环 2 的真实形态:** 6 次运行以「一大段 thinking 然后什么都没有」结束。stream 的 `complete` 事件显示 `</think>` 之后还有 25–60 个 output token 没有变成 text 或 toolRequest。
  直接打 Ollama 复现(绕开解析器让原文落到 content 里):模型写的是
  `{"name": "edit", "arguments": {"before": "print(f\"Hello, {name}!")", ...}}` —— 字符串里的引号没转义,JSON 非法,Ollama 丢掉整个调用,Goose 收到空消息就结束。6 次抽样 3 次非法。
  关 thinking(`think=false`)复现 5 次:4 次调用成功、1 次同样被吞;**不是 thinking 的锅**。
- **t08_r2(环 6):** `grep ... > errors.txt` 三次都成功了,但工具返回 `(no output)`,模型把它当失败反复重试,最后还汇报「没有 ERROR」。文件其实是对的。真实原因是**环 5(没读懂工具返回)**,不是循环设计。
- **t12_r3:** 前提错误题,模型没读文件就把 `message` 改成 `msg`。盲从。t12_r1/r2 「通过」是因为调用被吞、什么都没做 —— 已加 `tool_calls_min` check 堵上这个漏洞。
- **t11 r1/r3:** 其实答对了(「未找到 settings.yaml」),是我的关键字列表没覆盖「未找到」。已修,用 `regrade.py` 重判。
- 两次 `rg: command not found`:模型默认 ripgrep 存在。
- 上下文 16k 全程没撞到(环 7 为 0),最长一次 t08_r2 七次调用也没溢出。

**结论 / 下一步:**
- 走决策树:环 2 占主导 → 模型结构化输出问题。但形态很具体(引号转义),**不是「模型太小不会调工具」**,单步题 15/15 说明基本链路稳。
- 硬件结论:**暂不买。** 70B 模型会不会同样写错 JSON 转义,不知道;而免费对策有三个可以先试(见待办)。
- 下一步按顺序、每次一个变量:toolshim → 换模型家族 → 8b 对照。
