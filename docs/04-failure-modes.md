# 04 · 七环:失败模式分类

> 这是本仓库的核心诊断框架。`scripts/analyze.py` 按这个分类统计。

任何一环出问题,最终表现都是「回答不对」,但**原因完全不同,修法完全不同**。不打日志根本分不清。

---

## 七个环节

### 环 1 · 模型根本不调用工具
**症状:** 直接凭记忆编了个答案,压根没碰检索。
**原因:** 工具描述太模糊,或模型 tool calling 训练不够。
**修:** 改工具 description / 系统提示 / **换模型**。
**这是本地小模型最常见的第一道坎。**

### 环 2 · 调用了,但格式不对
**症状:** 输出一段像 JSON 但解析失败的文本;参数名拼错;少了必填字段;吐成裸文本或畸形 XML。
**原因:** 模型结构化输出能力不足。
**修:** **换更大的模型**,或改用 Code mode 绕开多轮 function call。
**⚠️ 这一环会累积:** 单轮 95% 正确,连续 5 轮就掉到 77%(0.95⁵)。

### 环 3 · 选错工具或参数值不合理
**症状:** 格式没问题,但检索词很糟。问「某型号压缩机不启动」,它去检索「HVAC」。
**原因:** 推理质量问题,不是格式问题。
**修:** few-shot 示例、更好的工具描述、换模型。

### 环 4 · 工具本身返回垃圾
**症状:** 调用完全正确,但返回的 chunk 不相关。
**原因:** **锅在 RAG,跟 agent 无关。** chunk 策略、embedding、重排序背这个责任。
**修:** 改 domain-mcp,不要改 agent。
**⚠️ 换再大的模型也救不了这一环。**

### 环 5 · 拿到好结果但没用上
**症状:** 检索结果里明明有答案,回答却跟它无关,或只用了第一条。
**原因:** 上下文太长被稀释;提示词没强制基于证据回答。
**修:** 上下文工程、强制引用、减少注入量。

### 环 6 · 循环不收敛
**症状:** 反复调同一个工具;换汤不换药地搜五轮;或证据明显不够就急着下结论。
**原因:** 终止条件设计问题。
**修:** 改循环控制、加最大轮次、加「证据是否充分」的显式判断。

### 环 7 · 上下文溢出
**症状:** 跑到第 6、7 轮忘了最初的问题。
**原因:** **本地模型的有效上下文往往远小于标称值。**
**修:** 压缩历史、用 subagent 隔离、减少每轮注入量。

## 快速对照:失败集中在哪 → 该做什么

| 集中在 | 说明 | 行动 |
|---|---|---|
| **环 1、2** | 模型能力不够 | **换模型**(→ 硬件投资有意义,见 `06-hardware.md`) |
| **环 3** | 推理质量 | 先试提示工程,不行再换模型 |
| **环 4** | RAG 问题 | **改 domain-mcp,买机器完全无用** |
| **环 5、7** | 上下文工程 | 软件问题,不花钱 |
| **环 6** | 循环设计 | 软件问题,不花钱 |

> **这张表是买不买 Mac 的决策依据。** 详见 `06-hardware.md`。

## 怎么定位

### 唯一正确的方法

把每一轮的**原始请求和原始响应**都落盘 —— 不是渲染后的界面文字,是:
- 发给模型的完整 prompt(含系统提示、工具定义、历史)
- 模型吐回来的原始 token(含未解析的 tool call 文本)
- 工具实际收到的参数
- 工具返回的原始结果

然后从头读一遍。**第一个「不对劲」出现在哪轮、哪个字段,就是崩的那一环。**

### 关键原则

**只算第一个失败环。** 一次运行崩在环 2,后面环 3-7 全是连带的,不单独计数——否则统计会被污染,看不出真正的瓶颈。

### 工具支持

| Harness | 能力 |
|---|---|
| Goose | verbose/debug 模式导出 |
| DeepSeek Harness | **Trajectory View** —— append-only 事件流,支持 resume / fork / search / replay |

**fork + replay 特别有用:** 从崩掉那一轮分叉重跑,只改一个变量(提示词/模型/工具描述),直接看是不是修好了。这是最快的迭代方式。
