# 05 · 基线测试计划

**目标:拿到一张失败分布表。在此之前不做任何架构或采购决策。**

---

## 为什么这件事排第一

三个待决问题——换模型?改 RAG?买 Mac?——**答案全都藏在同一张表里**,而这张表零成本、两天能拿到。

不测就选,是在赌。赌错的代价:三千美元,或者三个月。

---

## 测什么

### 指标 1 · 工具调用格式正确率(最关键)
连续 N 轮调用,每轮的 tool call 是否为合法结构化调用。

**判据线:**
| 正确率 | 结论 |
|---|---|
| **≥ 90%** | 模型够用,瓶颈在别处 → 别买机器,去改 RAG |
| **70–90%** | 边缘。先试 Code mode / 提示工程,不行再考虑硬件 |
| **< 70%** | 模型不够 → **硬件投资有明确价值** |

### 指标 2 · 七环失败分布
每次失败归到第一个出问题的环。见 `04-failure-modes.md`。

### 指标 3 · 端到端答案质量
人工标注:答案正确吗?引用的来源对吗?

---

## 怎么测

### 第一步:准备题目(最重要,别跳过)

`evals/questions.jsonl`,至少 20 条,**必须是真实技师问过的问题**。

不要自己编。自己编的问题会不自觉地写成「模型容易答对的样子」,测出来的数字是假的。去翻工单、问服务部门、看历史聊天记录。

格式见 `evals/README.md`。

### 第二步:跑

```bash
python3 scripts/run_eval.py \
    --config configs/goose.yaml \
    --questions evals/questions.jsonl \
    --repeat 3
```

`--repeat 3` 是因为同一个问题跑三遍结果可能不同 —— **要看的是稳定性,不是单次表现**。20 题 × 3 遍 = 60 次运行。

### 第三步:分析

```bash
python3 scripts/analyze.py runs/2026-09-05/
```

输出一张表:每一环各占多少失败。

### 第四步:人工过一遍 trajectory

**脚本只能做粗分类,环 3/4/5 的区别机器判断不准,必须人看。**

至少手工读 10 条失败的完整 trajectory。这一步花的时间最值。

## 决策树

```
拿到失败分布表
│
├─ 环 1、2 占多数(格式/不调用)
│   → 模型能力瓶颈
│   → 先试 DeepSeek Harness 的 Code mode(免费,可能直接解决)
│   → 仍不行 → 硬件投资有意义,M5 Max 128GB
│
├─ 环 4 占多数(检索结果差)
│   → RAG 问题,买机器无用
│   → 改 chunk 策略 / 加重排序 / 改 embedding
│   → 工作全在 domain-mcp 仓库,不在这里
│
├─ 环 3 占多数(选错工具/参数)
│   → 先改工具 description、加 few-shot
│   → 便宜,先试
│
├─ 环 5、6、7 占多数(上下文/循环)
│   → 纯软件问题,不花钱
│   → 上下文工程 + 终止条件设计
│
└─ 分布很平均
    → 说明还没到瓶颈期,基础链路就不稳
    → 回去检查配置,而不是优化任何单点
```

## 硬性纪律

1. **每次只改一个变量。** 同时换模型和改提示词,你不知道是哪个起的作用。
2. **原始 trajectory 全部落盘。** 渲染后的文字没有诊断价值。
3. **只算第一个失败环。** 后续连带失败不计,否则统计被污染。
4. **结论写进 `notes/findings.md`,带日期。** 三周后你会忘记为什么做了某个选择。
