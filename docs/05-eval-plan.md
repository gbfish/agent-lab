# 05 · 基线测试计划

**目标:拿到一张失败分布表。在此之前不做任何架构或采购决策。**

---

## 为什么这件事排第一

三个待决问题——换模型?改提示词 / 工具描述?买 Mac?——**答案全都藏在同一张表里**,而这张表零成本、两天能拿到。

不测就选,是在赌。赌错的代价:三千美元,或者三个月。

---

## 测什么

### 指标 1 · 工具调用格式正确率(最关键)
每次运行,模型发起的 tool call 是否为合法结构化调用(没崩在环 1 / 环 2)。

**判据线:**
| 正确率 | 结论 |
|---|---|
| **≥ 90%** | 模型够用,瓶颈在别处 → 别买机器,去修软件问题 |
| **70–90%** | 边缘。先试提示工程 / 减少工具数,不行再考虑硬件 |
| **< 70%** | 模型不够 → **硬件投资有明确价值** |

### 指标 2 · 任务完成率 + 每题稳定性
`checks` 全过才算过。同一题 3 次有过有不过的,是最值得读 trajectory 的。

### 指标 3 · 七环失败分布
每次失败归到第一个出问题的环。见 `04-failure-modes.md`。

---

## 怎么测

### 第一步:任务集

`evals/tasks.jsonl` 已带 12 条起步。格式和配比见 `evals/README.md`。加题的铁律:**必须能自动判分**。

### 第二步:跑

```bash
python3 scripts/run_eval.py --model qwen3:14b-16k --repeat 3 --tag baseline
```

`--repeat 3` 是因为同一个任务跑三遍结果可能不同 —— **要看的是稳定性,不是单次表现**。12 题 × 3 遍 = 36 次,14b 在本机 1–2 小时(t07 一次 240s)。

每次运行的产物在 `runs/<日期_时间>/<tid>_r<n>/`:`record.json`(命令、原始 stdout/stderr、判分)、`session.json`(完整对话)、`work/`(沙箱目录,事后可以进去看它到底改了什么)。

### 第三步:分析

```bash
python3 scripts/analyze.py runs/<日期_时间>/ --verbose
```

改了某题的 `checks` 之后不用重跑,`python3 scripts/regrade.py runs/<目录>/` 重判。

### 第四步:人工过一遍 trajectory

**脚本只能做粗分类,环 3 / 环 5 的区别机器判断不准,必须人看。**

至少手工读 10 条失败的 `session.json`。这一步花的时间最值。

## 决策树

```
拿到失败分布表
│
├─ 环 1、2 占多数(格式/不调用)
│   → 先排除上下文问题(_meta.json 里 ollama_context_length ≥ 16384?)
│   → 排除后仍是 → 模型能力瓶颈
│   → 先换 qwen3:14b(免费)
│   → 仍不行 → 硬件投资有意义,M5 Max 128GB 跑 70B 级
│
├─ 环 3 占多数(选错工具/参数)
│   → 先改 --system 提示、加 few-shot
│   → 便宜,先试
│
├─ 环 4 占多数(工具报错且没恢复)
│   → 看工具返回给模型的错误文本是否可读
│   → 通常是提示词 / 工具输出格式问题,不花钱
│
├─ 环 5、6、7 占多数(上下文/循环)
│   → 纯软件问题,不花钱
│   → 上下文工程 + 终止条件设计
│
└─ 分布很平均
    → 说明还没到瓶颈期,基础链路就不稳
    → 回去检查配置,而不是优化任何单点
```

## 硬性纪律

1. **每次只改一个变量。** 同时换模型和改提示词,你不知道是哪个起的作用。`--tag` 写清楚。
2. **原始 trajectory 全部落盘。** 渲染后的文字没有诊断价值。
3. **只算第一个失败环。** 后续连带失败不计,否则统计被污染。
4. **结论写进 `notes/findings.md`,带日期。** 三周后你会忘记为什么做了某个选择。
